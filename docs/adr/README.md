# 架构决策记录（ADR）

本目录记录那些「一旦定下就很难改」的技术与架构决策。每条决策一个文件，编号连续，只增不改；决策被推翻时新增一条 ADR 并将其状态改为「已废弃」，而不是删除原文。

## 什么时候需要写 ADR

出现以下任一情况时，应当新增 ADR：

- 引入或替换核心技术（框架、数据库、消息队列、编辑器）。
- 确定目录结构、分层方式或跨模块依赖规则。
- 做出会影响多人协作方式的决定（分支策略、发布方式、部署拓扑）。
- 在两个以上合理方案之间做了取舍，并希望后来者知道「为什么不选另一个」。

以下情况不需要 ADR：修 bug、加一个接口、调整字段长度、局部重构。

## 文件命名

```text
NNNN-kebab-case-title.md
```

编号从 `0001` 开始，四位补零；标题使用英文 kebab-case，正文使用中文。

## 模板

```markdown
# ADR-NNNN：一句话标题

- 状态：提议中 / 已接受 / 已废弃 / 已替代（被 ADR-xxxx 替代）
- 日期：YYYY-MM-DD
- 决策者：项目组

## 背景

为什么现在必须做这个决定？约束是什么？

## 决策

我们决定做什么？用简短、可执行的句子写清楚。

## 备选方案

至少列出两个被认真考虑过的方案，说明优缺点与结论。

## 后果

- 正面结果
- 需要承担的成本

## 约束

这个决定对后续代码和文档施加了哪些硬性要求？
```
